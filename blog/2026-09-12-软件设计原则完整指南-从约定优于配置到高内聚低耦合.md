# 除了"约定优于配置"，这7条软件设计原则同样值得掌握

> 做软件开发久了，你会发现一个规律：好的架构和烂的架构，差距往往不在技术选型，而在「设计原则」的贯彻程度。
> 
> 很多人听过"约定优于配置""组合优于继承"，但其实这类经典设计原则远不止这两条——它们核心都围绕三件事：**减少决策成本、降低模块耦合、提升长期可维护性**。
> 
> 今天我们把最常用的7条原则一次性讲透，配上微服务落地案例和避坑指南，看完就能用在项目里。

## 写好一个增删改查，没那么容易

新手程序员常常会有这样的疑惑：一个简单的增删改查（CRUD），为什么前辈们要套上一层又一层的 Controller / Service / Repository / DTO / VO？直接在接口里拼 SQL、操作数据库，几分钟不就搞完了吗？

**写一个能跑的增删改查，确实容易**——几张表、几个接口、几条 SQL，半天就能上线。但**想写好一个增删改查，却远没有那么简单**：

- **校验规则怎么放？** 参数校验写在 Controller 里，一旦校验规则变化就要改接口；抽成独立的 Validator，新增/删除校验只要改一处，符合单一职责。
- **数据访问层为什么要抽象？** 今天用 MySQL，明天换 PostgreSQL，后天又要加分库分表，直接在业务代码里写死 JDBC 调用，每次迁移都得改遍所有 Service；抽出一个 `UserRepository` 接口，业务层只依赖抽象，符合依赖倒置。
- **返回结构为什么不直接返回实体？** 把数据库实体直接丢给前端，字段一变接口契约就跟着崩；用 VO/DTO 隔离内部模型与对外契约，符合开闭原则——内部表结构可以改，对外接口契约稳定不变。
- **新需求来了要不要改老代码？** 原来只支持按 ID 查询，现在要加按手机号、按注册时间区间查询。直接在原方法里堆 `if-else`，三个月后这个方法会变成几百行的"神函数"；通过策略模式或规约模式（Specification）扩展查询条件，新增条件只加新类，符合开闭原则。
- **同样的增删改查为什么还要再封一层？** 每个业务模块都有列表分页、按字段排序、软删除、操作日志……这些是跨模块的通用能力，不抽出来就是每个 Service 重复写一遍；抽成基类或组合组件，就是组合优于继承的落地。

你看，同一个"增删改查"，朴素写法几小时搞定，但后续每加一个需求、每做一次迁移、每改一个字段，都要付出成倍的修改成本；而按设计原则组织好的代码，初期多花一两天，换来的却是**几年内需求变化时的从容不迫**。

这就是设计原则的价值——它不是把简单问题搞复杂，而是把"将来一定会变复杂的问题"提前用结构约束住，让变化的影响范围始终可控。

带着这个视角，我们再来看下面这 7 条原则，你会发现它们不是教科书上的教条，而是一条条从无数次返工中提炼出来的"避坑经验"。

## 一、7条核心设计原则，每条都能解决80%的架构问题

### 1. 约定优于配置（Convention over Configuration, CoC）
**核心逻辑**：框架预设一套合理的默认规则，开发者只需要处理偏离默认的特殊情况，不用为每个通用场景都写一遍配置。

最典型的例子就是 Spring Boot：
- 引入 `spring-boot-starter-web` 就自动内置 Tomcat，不用手动配置服务器
- 默认按类名映射数据库表名（`User` 类对应 `user` 表），字段名不一致时才需要 `@Column` 显式指定
- 主启动类放在根包下，自动扫描同包及子包的组件，不用写 `<context:component-scan>`

相比传统 SSM 项目动辄几百行的 XML 配置，Spring Boot 靠约定把配置量减少了 80% 以上。

### 2. 组合优于继承（Composition over Inheritance）
**核心逻辑**：优先通过对象组合的方式扩展行为，而不是依赖类继承。继承是"白盒复用"，父类的内部细节对子类完全可见，很容易破坏封装；组合是"黑盒复用"，对象之间只通过接口交互，耦合度更低、更灵活。

举个游戏角色的例子：
- 用继承的话，你得写 `Hero` → `Warrior` → `MagicWarrior` → `FlyingMagicWarrior` 一长串继承链，加个新特性就得改父类，牵一发动全身
- 用组合的话，把「攻击方式」「移动方式」「技能系统」拆成独立模块，需要什么组合什么，加新能力只要加新模块，完全不影响已有代码

GoF 的《设计模式》里有句名言："优先使用对象组合，而不是类继承"，这句话可以说是面向对象设计的黄金准则。

### 3. 依赖倒置原则（Dependency Inversion Principle, DIP）
**核心逻辑**：高层模块不依赖低层模块，两者都依赖抽象；抽象不依赖细节，细节依赖抽象。

说白了就是：**不要面向实现编程，要面向接口编程**。

比如你做一个支付系统，一开始只接支付宝，直接在业务代码里写 `AlipayService.pay()`，后面要加微信支付、银联支付，就得改遍所有调用的地方。
如果一开始就定义一个 `PaymentService` 接口，业务代码只依赖这个接口，后面加新的支付方式只要加实现类，业务代码一行都不用改——这就是依赖倒置的价值。

### 4. 好莱坞原则（Hollywood Principle）
**核心逻辑**："不要打电话给我们，我们会打电话给你"（Don't call us, we'll call you）。组件自己不控制流程，由上层容器统一管理生命周期和调用时机。

先把这个比喻本身讲清楚——这句话来自好莱坞影视行业的试镜流程：

- **谁给谁打电话？** 试镜的演员（新人/求职者）给剧组选角导演打电话
- **为什么说"不要打电话给我们"？** 试镜结束后，演员往往会焦急地反复打电话追问"我通过了吗？什么时候有结果？"，剧组被一堆询问电话骚扰不堪其扰，于是统一回应："不要打电话给我们"
- **"我们会打电话给你"是什么意思？** 意思是：如果你被选中了，我们会主动通知你；如果没接到电话，就说明没被选中。**结果的通知时机和方式，由剧组（高层）决定，不由演员（底层）催促**

对应到软件架构里，角色就清晰了：

| 好莱坞场景 | 软件架构场景 |
| --- | --- |
| 剧组选角导演 | 框架 / IoC 容器 / 上层调度者 |
| 试镜的演员 | 业务组件 / 业务对象 |
| 演员主动打电话追问结果 | 业务代码主动调用容器获取依赖、控制流程 |
| 剧组主动通知选中的演员 | 容器主动调用业务组件的生命周期方法（初始化、注入、销毁） |

这就是控制反转（IoC）的核心思想：
- 传统开发是业务代码自己 new 对象、自己调方法，控制权在开发者手里——相当于演员自己跑到剧组办公室问"今天有我的戏份吗"
- IoC 容器里，对象的创建、初始化、销毁全由 Spring 管，业务代码只需要声明"我需要一个 UserService"，容器就会自动注入——相当于演员只留下"我有空、能演军人角色"的信息，剧组需要时自然会来通知

你写的业务代码从来不会主动调用 `ApplicationContext.getBean()`，都是 Spring 在调用你的代码——这就是典型的"好莱坞式"控制权反转。

好莱坞原则的价值在于：**让"调度者"和"被调度者"彻底解耦**。容器不需要知道业务组件的具体实现，业务组件也不需要知道容器何时会调用它，双方只通过约定好的方法名（生命周期回调、接口契约）沟通。一旦组件不再自己控制流程，新增一个业务组件就是丢进容器的事，不需要改任何已有代码。

### 5. 开闭原则（Open/Closed Principle, OCP）
**核心逻辑**：对扩展开放，对修改关闭。新需求通过新增代码实现，而不是修改已有稳定代码。

为什么叫"开闭"？因为它同时做到了两件事：
- **开放**：功能可以被扩展，新需求能加进来
- **关闭**：已有稳定代码不被修改，不会因为加新功能把老功能搞挂

最经典的实现方式就是多态：定义抽象接口，不同场景写不同实现，新增场景加新实现类，原有逻辑完全不动。
很多人觉得开闭原则是"理想主义"，但实际上，只要你把"经常变的部分"和"稳定的部分"拆分开，大部分业务场景都能做到基本符合开闭原则。

### 6. 单一职责原则（Single Responsibility Principle, SRP）
**核心逻辑**：一个类（或模块）应该只有一个引起它变化的原因。换句话说，一个类只做一件事。

很多人对单一职责的理解有误区：不是说类越小越好，而是**变化的原因只有一个**。
比如一个 `UserService` 里既写用户注册逻辑，又写订单查询逻辑，那用户规则变了要改它，订单规则变了也要改它，这就违反了单一职责——两个完全不同的变化原因揉在一个类里，改的时候很容易互相影响。

职责单一的模块，内聚性更高，复用性更强，出问题也更容易定位。

### 7. 高内聚、低耦合（High Cohesion, Low Coupling）
**核心逻辑**：模块内部的元素联系越紧密越好（高内聚），模块之间的依赖越少越好（低耦合）。

- **高内聚**：把相关的功能放在一起，一个模块就干好一件事，不东一榔头西一棒子
- **低耦合**：模块之间尽量少依赖、弱依赖，别你中有我我中有你，改一个模块全系统都要跟着改

这可以说是软件架构的终极评价标准——好的架构，一定是模块内部高度凝聚，模块之间松耦合的。
很多人说"微服务拆完更难维护了"，本质就是拆的时候没做到高内聚低耦合：把一个完整的功能拆到两个服务里，耦合反而更高了。

## 二、落地案例："约定优于配置"在微服务架构中的实践
光说原则太抽象，我们拿最典型的"约定优于配置"来看看，它在微服务架构里到底是怎么落地的。

### 1. Spring Boot 基础层：把通用配置全部内置
Spring Boot 可以说是把 CoC 贯彻到极致的框架：
- **Starter 约定**：官方提供场景化启动器，引入 `spring-boot-starter-web` 就自动配好 Spring MVC、Jackson、文件上传等一整套组件，不用自己一个个导依赖、调版本
- **目录结构约定**：预设 `src/main/java` 源码目录、`src/main/resources` 配置目录、`src/test/java` 测试目录，不用再手动配置构建路径
- **自动配置约定**：基于 classpath 下的依赖自动完成组件初始化，检测到有数据库驱动就自动配置数据源，检测到有 Redis 依赖就自动配置 RedisTemplate

### 2. Spring Cloud 治理层：把分布式能力标准化
到了微服务层面，约定的价值就更明显了：
- **服务注册发现约定**：服务启动自动向注册中心（Eureka/Nacos）上报实例信息，消费者直接通过服务名调用，不用硬编码 IP 和端口
- **负载均衡约定**：Ribbon 默认集成在调用链路中，默认轮询策略，不用额外配置就能实现客户端负载均衡
- **配置中心约定**：默认按 `服务名-环境.yml` 的格式拉取配置，自动区分 dev/test/prod 环境，不用每个环境手动改配置文件

### 3. 生产级优化：约定帮你踩过坑
很多生产级的优化，其实也是靠约定实现的：
- **心跳续约约定**：Eureka 默认 30 秒一次心跳，90 秒未收到自动剔除实例，这套默认参数适配 90% 以上的生产场景
- **配置刷新约定**：Spring Cloud Config 默认 30-60 秒刷新一次远程仓库，启动时预克隆仓库，把首次配置请求从秒级降到毫秒级
- **熔断降级约定**：Sentinel 默认的流控规则、降级阈值，都是基于大量生产数据总结出来的最优值，小项目直接用就行，不用自己慢慢调参

## 三、落地避坑清单：这些原则用错反而更糟
设计原则是"指导思想"，不是"金科玉律"，用错了反而会起反作用。这里整理了6个最常见的坑：

| 常见坑点 | 具体表现 | 避坑建议 |
| --- | --- | --- |
| 约定不透明 | 全靠默认约定，出了问题不知道哪的问题，排查困难 | 保留约定的可覆盖能力，文档化所有默认约定，关键配置显式声明 |
| 过度继承 | 为了复用代码滥用继承，继承链长达五六层，改父类全链子类都受影响 | 优先用组合，继承只用于严格的"is-a"场景，继承链不要超过3层 |
| 开闭原则过度设计 | 为了"未来可能扩展"提前抽象出七八层接口，实际根本用不上 | 第一次出现不改，第二次重复出现时再抽象，别为了1%的可能性加99%的复杂度 |
| 单一职责走极端 | 把类拆得越来越细，一个功能要调七八个类，类数量爆炸 | 以"变化频率"为标准，变化频率相同的职责可以放一起，不是越细越好 |
| 依赖倒置滥用 | 每个类都抽一个接口，美其名曰"解耦"，实际接口只有一个实现，完全是冗余 | 只有预期会有多种实现、或者需要隔离外部依赖时才抽接口，不要为了解耦而解耦 |
| 模块拆太碎 | 为了"低耦合"把模块拆得稀碎，一个完整流程跨七八个模块，调用链巨长 | 内聚和耦合要平衡，优先保证高内聚，不要为了低耦合把一个完整功能拆得七零八落 |

## 写在最后
很多人觉得"设计原则"是虚的，不如学个框架、学门语言实在。但你做技术越久就越会发现：
> 框架会过时，语言会迭代，但那些经过几十年验证的设计原则，永远是你判断架构好坏、做技术决策的底层依据。

这7条原则不需要你一次性全做到，也不需要在每个场景都严格套用——你只要在写代码、做设计的时候，多问自己一句：
"这么写，是不是符合'减少决策、降低耦合、提升可维护性'这三个目标？"

就这一句话，就能帮你避开80%的烂设计。
