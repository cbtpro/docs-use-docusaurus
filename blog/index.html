next-ai-draw-io Docker Compose 部署与长期维护

2026年9月30日 · 阅读需 11 分钟
cbtpro
Front End Engineer

项目介绍​

next-ai-draw-io 是一个结合 AI 与 draw.io 的图表生成工具，可以通过自然语言生成和修改 draw.io 图表，并支持多种 AI Provider。

项目地址：

https://github.com/DayuanJiang/next-ai-draw-io

Docker 部署文档：

https://github.com/DayuanJiang/next-ai-draw-io/blob/main/docs/cn/docker.md

Docker 镜像：

ghcr.io/dayuanjiang/next-ai-draw-io:latest

默认服务端口：

3000

本文采用：

Docker Compose
      +
.env
      +
本地持久化目录
      +
Docker Named Volume
      +
upgrade.sh

进行部署和长期维护。

目录规划

统一将 Docker 相关文件存放到：

~/Developer/docker/

最终目录结构：

~/Developer/docker/
│
├── next-ai-draw-io/
│   ├── docker-compose.yml
│   ├── .env
│   ├── .env.example
│   ├── .gitignore
│   └── upgrade.sh
│
└── next-ai-draw-io-data/
    └── 持久化数据

其中：

~/Developer/docker/next-ai-draw-io

用于保存 Docker Compose 配置和维护脚本。

~/Developer/docker/next-ai-draw-io-data

用于保存持久化数据。

Docker 中创建：

next-ai-draw-io-data

Named Volume。

最终关系：

Docker Container
next-ai-draw-io
        │
        ▼
Docker Volume
next-ai-draw-io-data
        │
        ▼
~/Developer/docker/next-ai-draw-io-data

这样 Container 可以随时删除和重新创建，而数据独立保存在宿主机。

创建目录

执行：

mkdir -p ~/Developer/docker/next-ai-draw-io
mkdir -p ~/Developer/docker/next-ai-draw-io-data

进入配置目录：

cd ~/Developer/docker/next-ai-draw-io

检查：

ls -lah ~/Developer/docker/

应该存在：

next-ai-draw-io/
next-ai-draw-io-data/

创建 Docker Volume

创建：

next-ai-draw-io-data

Docker Named Volume，并绑定宿主机目录：

docker volume create \
  --driver local \
  --opt type=none \
  --opt o=bind \
  --opt device="$HOME/Developer/docker/next-ai-draw-io-data" \
  next-ai-draw-io-data

这个命令只需要执行一次。

检查 Volume：

docker volume inspect next-ai-draw-io-data

应该可以看到类似：

[
  {
    "Name": "next-ai-draw-io-data",
    "Driver": "local",
    "Options": {
      "device": "/Users/username/Developer/docker/next-ai-draw-io-data",
      "o": "bind",
      "type": "none"
    }
  }
]

重点确认：

Name
    next-ai-draw-io-data

device
    ~/Developer/docker/next-ai-draw-io-data

创建 .env

进入：

cd ~/Developer/docker/next-ai-draw-io

创建：

.env

例如使用 OpenAI：

# Docker
NEXT_AI_DRAW_IO_VERSION=latest
NEXT_AI_DRAW_IO_PORT=3000

# AI
AI_PROVIDER=openai
AI_MODEL=gpt-4o

OPENAI_API_KEY=your_api_key

将：

your_api_key

替换为自己的 API Key。

OpenAI 兼容 API

如果使用兼容 OpenAI API 的第三方服务，可以增加：

AI_PROVIDER=openai
AI_MODEL=gpt-4o

OPENAI_API_KEY=your_api_key
OPENAI_BASE_URL=https://your-api.example.com/v1

其中：

OPENAI_BASE_URL

用于指定自定义 API Endpoint。

DeepSeek 配置

如果使用 DeepSeek：

NEXT_AI_DRAW_IO_VERSION=latest
NEXT_AI_DRAW_IO_PORT=3000

AI_PROVIDER=deepseek
AI_MODEL=deepseek-chat

DEEPSEEK_API_KEY=your_api_key

如果需要自定义 API 地址：

DEEPSEEK_BASE_URL=https://your-custom-endpoint

Gemini 配置

例如：

AI_PROVIDER=google
AI_MODEL=gemini-2.0-flash

GOOGLE_GENERATIVE_AI_API_KEY=your_api_key

自定义地址：

GOOGLE_BASE_URL=https://your-custom-endpoint

Anthropic 配置

例如：

AI_PROVIDER=anthropic
AI_MODEL=claude-sonnet-4-5-20250514

ANTHROPIC_API_KEY=your_api_key

也可以使用：

ANTHROPIC_AUTH_TOKEN=your_auth_token

ANTHROPIC_API_KEY 和 ANTHROPIC_AUTH_TOKEN 根据实际认证方式选择，不建议同时配置。

Ollama 本地模型

如果使用宿主机上的 Ollama：

AI_PROVIDER=ollama

AI_MODEL=llama3.2

OLLAMA_BASE_URL=http://host.docker.internal:11434

Docker Container 内部：

localhost

指向的是 Container 自己，而不是宿主机。

因此在 macOS / Windows Docker Desktop 环境中，访问宿主机服务通常使用：

host.docker.internal

而不是：

localhost

创建 .env.example

建议同时创建：

.env.example

内容：

# Docker
NEXT_AI_DRAW_IO_VERSION=latest
NEXT_AI_DRAW_IO_PORT=3000

# AI Provider
AI_PROVIDER=openai
AI_MODEL=gpt-4o

# OpenAI
OPENAI_API_KEY=
OPENAI_BASE_URL=

以后重新部署时可以：

cp .env.example .env

然后修改：

vim .env

创建 docker-compose.yml

创建：

docker-compose.yml

内容：

services:
  next-ai-draw-io:
    image: ghcr.io/dayuanjiang/next-ai-draw-io:${NEXT_AI_DRAW_IO_VERSION:-latest}

    container_name: next-ai-draw-io

    restart: unless-stopped

    stop_grace_period: 30s

    ports:
      - "127.0.0.1:${NEXT_AI_DRAW_IO_PORT:-3000}:3000"

    env_file:
      - .env

    volumes:
      - next-ai-draw-io-data:/app/data

volumes:
  next-ai-draw-io-data:
    external: true

这里：

external: true

表示：

next-ai-draw-io-data

由 Docker 独立管理，而不是由当前 Compose Project 创建。

因此执行：

docker compose down

不会删除该 Volume。

持久化关系

最终数据关系：

next-ai-draw-io
    Container
        │
        │ /app/data
        ▼
next-ai-draw-io-data
    Docker Volume
        │
        │ bind
        ▼
~/Developer/docker/next-ai-draw-io-data

Container：

可删除
可重新创建
可升级

Volume：

长期保留

宿主机目录：

长期保留
方便备份
方便迁移

检查 Compose 配置

执行：

docker compose config

重点检查：

image
ports

volumes

例如镜像应该解析成：

ghcr.io/dayuanjiang/next-ai-draw-io:latest

Volume：

拉取镜像：

docker compose pull

启动：

docker compose up -d

也可以：

docker compose pull && docker compose up -d

查看运行状态

执行：

docker compose ps

或者：

docker ps --filter name=next-ai-draw-io

正常情况下：

next-ai-draw-io

应该处于：

Up

状态。

访问应用

浏览器打开：

http://127.0.0.1:3000

或者：

http://localhost:3000

如果修改：

NEXT_AI_DRAW_IO_PORT=3010

则访问：

http://127.0.0.1:3010

为什么绑定 127.0.0.1

Compose 中使用：

ports:
  - "127.0.0.1:${NEXT_AI_DRAW_IO_PORT:-3000}:3000"

表示服务只允许本机访问。

这样更加适合：

  • 本机使用
  • Nginx 反向代理
  • Caddy 反向代理
  • Cloudflare Tunnel
  • 其他网关代理

不会直接把：

3000

端口暴露给整个局域网。

如果需要局域网访问

将：

ports:
  - "127.0.0.1:${NEXT_AI_DRAW_IO_PORT:-3000}:3000"

修改为：

ports:
  - "${NEXT_AI_DRAW_IO_PORT:-3000}:3000"

相当于：

0.0.0.0:3000

局域网设备就可以通过：

http://宿主机IP:3000

访问。

如果没有局域网访问需求，建议继续使用：

127.0.0.1

创建 upgrade.sh

为了简化长期维护，创建：

upgrade.sh

内容：

#!/usr/bin/env bash

set -Eeuo pipefail

cd "$(dirname "$0")"

echo "========================================"
echo " next-ai-draw-io Upgrade"
echo "========================================"

echo
echo "[1/4] Pull latest image..."

docker compose pull

echo
echo "[2/4] Update container..."

docker compose up -d

echo
echo "[3/4] Container status..."

docker compose ps

echo
echo "[4/4] Recent logs..."

docker compose logs \
  --tail 50 \
  next-ai-draw-io

echo
echo "========================================"
echo " Upgrade completed"
echo "========================================"

添加执行权限：

chmod +x upgrade.sh

日常升级

以后只需要：

cd ~/Developer/docker/next-ai-draw-io

./upgrade.sh

或者直接：

~/Developer/docker/next-ai-draw-io/upgrade.sh

脚本内部：

cd "$(dirname "$0")"

会自动切换到脚本所在目录。

固定版本

如果项目提供固定版本 Tag，例如：

v1.2.3

可以将：

NEXT_AI_DRAW_IO_VERSION=latest

修改为：

NEXT_AI_DRAW_IO_VERSION=v1.2.3

然后：

docker compose pull
docker compose up -d

这样不会自动跟随：

latest

更新。

对于长期稳定运行的服务，如果官方提供稳定版本 Tag，优先使用明确版本通常更容易控制升级节奏和回滚。

持久化数据备份

因为数据最终位于：

~/Developer/docker/next-ai-draw-io-data

建议备份前停止 Container：

tar -czf \
  ~/Developer/docker/next-ai-draw-io-data-$(date +%Y%m%d-%H%M%S).tar.gz \
  -C ~/Developer/docker \
  next-ai-draw-io-data

然后重新启动：

docker compose up -d

最终得到类似：

~/Developer/docker/
│
├── next-ai-draw-io/
├── next-ai-draw-io-data/
└── next-ai-draw-io-data-20260930-093000.tar.gz

数据恢复

停止：

cd ~/Developer/docker/next-ai-draw-io

docker compose stop

  ~/Developer/docker/next-ai-draw-io-data \
  ~/Developer/docker/next-ai-draw-io-data.old

tar -xzf \
  ~/Developer/docker/next-ai-draw-io-data-YYYYMMDD-HHMMSS.tar.gz \
  -C ~/Developer/docker

docker compose up -d

查看日志：

docker compose logs \
  --tail 100 \
  next-ai-draw-io

确认恢复成功后，再决定是否删除：

next-ai-draw-io-data.old

长期维护原则

整个部署可以归纳为：

Container
    │
    └── 可删除、可重新创建

Docker Image
    │
    └── 可升级、可替换

docker-compose.yml
    │
    └── Git 管理

.env
    │
    ├── AI Provider
    ├── Model
    ├── API Key
    └── 不提交 Git

Docker Volume
    │
    └── next-ai-draw-io-data
              │
              ▼
~/Developer/docker/next-ai-draw-io-data
              │
              └── 长期保存、定期备份

核心原则：

Container 和 Docker Image 都应该视为可替换资源，真正需要长期保护的是部署配置、API 配置以及持久化数据。

以后普通升级：

./upgrade.sh

重要版本升级：

停止服务
   ↓
备份 next-ai-draw-io-data
   ↓
阅读 Release Notes
   ↓
拉取新 Image
   ↓
重新部署
   ↓
检查日志
   ↓
验证 AI / draw.io 功能
   ↓
确认稳定后再清理旧 Image

这样即可形成一套适合长期维护的 next-ai-draw-io Docker 部署环境。

CRUD 之外 - 加密与签名在登录链路的位置

2026年9月29日 · 阅读需 6 分钟

Front End Engineer

登录接口的代码里，密码比对、验证码校验、设备指纹哈希，全是哈希函数和字符串比较，没有公钥私钥的影子。但一次登录走下来，非对称加密至少出现在两处：TLS 握手时服务端用证书私钥签名、客户端用证书公钥验签；登录成功后签 JWT 时服务端用签名私钥签、网关或客户端用公钥验。

这两次"签"和密码哈希是不同的事。教材里 RSA 把签名说成"用私钥解密一段摘要"，容易让人以为签名就是反向加密。它们的数学结构相似，目的完全不同。

CRUD 之外 - Token 防盗用的三层绑定

2026年9月29日 · 阅读需 10 分钟
cbtpro
Front End Engineer

登录接口签发的 Token 经常被直接返回给前端，前端放在 localStorage 或内存里，后续请求带在 Authorization 头里。Token 一旦泄露，攻击者就拥有了这个用户的所有能力，直到过期。过期时间设短，用户频繁掉线；设长，被盗的窗口也跟着拉长。

真正的问题不是 Token 会不会泄露，而是泄露之后攻击者能不能用。把 Token 和三个东西绑在一起：谁在用（用户身份）、在什么设备上用（设备指纹）、从哪个网络环境用（真实 IP）。三者同时匹配，Token 才有效。

CRUD 之外 - 登录链路的验证码、双 Token 与设备绑定

2026年9月28日 · 阅读需 25 分钟
cbtpro
Front End Engineer

登录接口的返回值,经常只是一个 JWT。验证码做完了、密码比对过了、权限码也下发了,剩下的都交给 Token 自己扛。但 Token 一旦被日志记录、被中间代理缓存、被 XSS 抓走,持有者就拥有了这个用户的所有能力,直到过期。过期时间设短,用户每隔十几分钟就要重登;设长,被盗的窗口也跟着拉长。

把登录拆开看,真正要做的事情是三件:证明这次请求是某个用户发的(认证)、把这次会话和一个不可转移的设备上下文绑起来(设备绑定)、在 Token 失效后能继续持有这个绑定关系而不让用户重输密码(刷新)。把它们糊在一个签发函数里,会让每一个安全决策都改不动,也补不齐。

CRUD 之外 - 数据接口权限的分层与切面

2026年9月24日 · 阅读需 24 分钟
cbtpro
Front End Engineer

列表上的"编辑"按钮被前端权限封装藏起来，并不意味着接口可以不鉴权。用户用 Postman 直接调 /api/orders/123，照样能改到别人的订单。前端权限只是减少误操作的服务体验，服务端必须自己挡住每一次请求。

数据接口的权限要分清三件事：这个请求是谁发的(认证)、能不能做这个动作(授权)、能看到或改动哪些数据(数据范围)。把它们混在一段拦截器里，会让规则散落、难以测试，也无法处理"只看本部门"这种需要改写 SQL 的需求。

CRUD 之外 - 防抖与节流的边界与误用

2026年9月24日 · 阅读需 10 分钟
cbtpro
Front End Engineer

用户输入框敲一个字查一次、拖拽时鼠标移动发了几百次事件、按钮被连点提交了两次订单。前端遇到这类高频事件，第一反应是"加个防抖"。但搜索框、拖拽、窗口调整、按钮连点这几个场景对"减少触发"的要求不一样。把防抖当银弹，要么首屏不动，要么用户停下来还在等。

防抖(debounce)和节流(throttle)表面都是"少触发几次"，实际触发策略完全不同。选错不是"少触发一点"的差别，是体验从流畅变卡顿的差别。
